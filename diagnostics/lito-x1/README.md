# DJI Lito X1 — живые замеры протокола (06.08.2026)

Снято с работающего борта через LAN API FreeFCC 1.5.64 (`/api/command`), пульт rc331,
DUML-порт борта 40007. Серийник борта `1581FB34C25CF0032AAG`, Wi-Fi SSID `DJI-LITOX1-C4AD`,
прошивка дрона 01.00.0300, прошивка пульта 10.00.0100.

## Файлы

- `params-table.jsonl` — таблица параметров FC, по одной записи на индекс.
  Прочитаны имена 875 из 1593; у остальных `"failed": true` — ответ не пришёл
  за отведённое время, их нужно дочитать повторным проходом.
- `duml-capture-40007.json` — пассивный захват шины, включая кадр с серийником.

## Доступ к параметрам

Хэш-доступ `03:F8` / `03:F9`, на котором построены профили `led_off.json`,
`led_on.json` и GPS-контроль, на этой прошивке **не работает**: `03:F8` отвечает
`payload=00` (голый retcode) на любой хэш, включая заведомо мусорный `deadbeef`.
Поэтому readback LED (`a259ceed`) и GPS (`829542c5`) не даёт значения, а запись
`03:F9` не подтверждается.

Работает индексный доступ:

```
03:E0  payload: u16 (что угодно)      -> retcode + hash таблицы + количество параметров (1593)
03:E1  payload: u16 table + u16 index -> описание параметра
```

Формат ответа `03:E1` (смещения от начала payload):

| смещение | поле |
|---|---|
| 0 | retcode (0 = ok, 9 = параметр не найден) |
| 1–3 | нули (резерв) |
| 4–5 | index, u16 LE |
| 6–7 | type_id, u16 LE |
| 8–9 | size значения в байтах, u16 LE |
| 10–13 | значение по умолчанию |
| 14–17 | минимум |
| 18–21 | максимум |
| 22… | имя, ASCIIZ |

Имена параметров отличаются от прежних прошивок — отсюда и промах старых хэшей:
GPS здесь называется просто `gps_enable` (индекс 650), а не `g_config.gps_cfg.gps_enable`.

## Ключевые параметры

| индекс | имя | size | дефолт | диапазон |
|---|---|---|---|---|
| 22 | `ext_led_ctrl` | 4 | 0 | 0…4294967295 |
| 23 | `forearm_led_ctrl` | 1 | 239 (0xEF) | 0…255 |
| 24 | `param_single_ledctrl_enable` | 4 | 255 | 0…255 |
| 26 | `param_hidden_ledctrl_enable` | 1 | 1 | 0…1 |
| 650 | `gps_enable` | 1 | 1 | 0…1 |

Дефолт `forearm_led_ctrl` совпадает со значением «LED ON» из `led_on.json`
(`a259ceedef`), то есть это тот же параметр, что гасит огни на прежних бортах.

## Чего найти не удалось

- **Команда записи значения.** `03:E2` и `03:E4` принимают payload, валидируют
  индекс (несуществующий остаётся без ответа) и отвечают `00000000`, но
  наблюдаемого эффекта на подсветку нет — проверено на живом борту, в том числе
  обёрнутым кадром и серией из 10 записей, как в профиле `led_off.json`.
  `03:E1` со значением в payload не отвечает вовсе.
- **Команда чтения значения.** Все параметры возвращают одинаковый ответ, то есть
  это retcode, а не данные. Текущее состояние LED и GPS прочитать нечем.
- **Алгоритм хэша.** Проверены пары `forearm_led_ctrl → 0xEDCE59A2` и
  `gps_enable → 0xC5429582` на 7 полиномах × 8 конфигураций CRC32 × 4 варианта
  префикса имени — совпадений нет.

Учитывать конфаундер: во время замеров на борту висели «Ошибка системы питания»,
«Ошибка подключения ESC» и «Лучи сложены». Не исключено, что FC отвергает запись
параметров в таком состоянии, — повторить на исправном борту.

## Серийник борта

Приходит кадром `sender=0xee dst=0x02 cmd_set=0x51 cmd_id=0x14 cmd_type=0x00`.
Это push, а не периодический broadcast: за 30 секунд наблюдения без активности
DJI Fly — ни одного такого кадра. Появляется, когда DJI Fly открывает экран
«Информация». Активный запрос `0x51/0x14` к `dst=0xee` возвращает retcode `0xE0`.

В таблице параметров серийника нет — среди известных имён только
`ETD6405_SN_Checked` / `_Matched` / `_No_Check`, это флаги проверки SN модуля.

Поэтому надёжный источник серийника — экран DJI Fly через accessibility,
а не DUML-пробник.

## Ограничения инструментов

- Пассивный захват на 40007 видит только входящий поток: все кадры адресованы
  `dst=0x02`, запросов самой DJI Fly не видно.
- `logcat_capture` бесполезен — `READ_LOGS granted=false`.
- Порт 40007 нельзя удерживать: DJI Fly теряет связь с бортом. Читать и отпускать.
