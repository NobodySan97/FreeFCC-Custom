# DJI Mini 5 Pro — контрольные замеры (06.08.2026)

Тот же пульт (rc331, `6UZBL7302102G9`), FreeFCC 1.5.64, порт борта 40007.
Снято сразу после Lito X1, чтобы отделить дефекты приложения от особенностей борта.

Борт: `WA150` / DJI Mini 5 Pro, серийник `1581F9DEC25AQ02998T5`.

## Хэш-доступ жив — в отличие от Lito X1

```
03:F8 a259ceed  -> 00 a259ceed ef     LED  = 0xEF (включён)
03:F8 829542c5  -> 00 829542c5 01     GPS  = 1 (включён)
03:F8 deadbeef  -> 00                 мусорный хэш: только retcode
```

Ответ ровно 6 байт — то, что ждёт `LedReadbackProtocol.parse`. Штатный путь
приложения работает целиком: `LED state read back: OFF`, `GPS state read back: ON`,
а запись подтверждается — `LED OFF verified after attempt 2/2`.

Значит `00` на любой хэш у Lito X1 означало «параметр не найден» для всех хэшей
сразу, а не поломку механизма `F8`: там просто другая таблица имён.

## Индексный доступ есть и здесь, и он информативнее

`03:E0` сообщает 1554 параметра (у Lito X1 — 1593). Формат `03:E1` тот же, но имя
содержит **две части через `|`**:

```
03:E1 table=0 index=23 -> forearm_led_ctrl|g_config.misc_cfg.forearm_lamp_ctrl
```

У Lito X1 в тех же записях только короткая часть (`forearm_led_ctrl`), канонических
`g_config.*` имён нет. Отсюда и промах старых хэшей на Lito X1.

Полное имя `g_config.misc_cfg.forearm_lamp_ctrl` соответствует хэшу `0xEDCE59A2`,
которым FreeFCC гасит огни. Перебор CRC32 (8 полиномов × конфигурации × варианты
префикса и завершающего нуля) совпадений не дал — хэш действительно не CRC32.

Искать его и не требовалось: алгоритм записан в
[`FLYC_PARAM_TABLE.md`](../../docs/FLYC_PARAM_TABLE.md) и
[`DUML_COMMAND_AUDIT.md`](../../docs/DUML_COMMAND_AUDIT.md) — `h = ((h << 8) | byte)
mod 0xfffffffb` над `имя + "_0"`. Он воспроизводит `0xEDCE59A2` и все остальные
известные хэши с провода. Вывод «алгоритм подобрать не удалось» из этой сессии
(06.08.2026) снят 07.08.2026.

## Серийник в шине есть постоянно

В отличие от Lito X1, где кадр с серийником приходил только при заходе DJI Fly
в «Информацию», здесь он появляется стабильно:

```
окно 3с #1: кадров=125  серийник встречен 2 раза
окно 3с #2: кадров=128  серийник встречен 2 раза
окно 3с #3: кадров=128  серийник встречен 2 раза
окно 3с #4: кадров=128  серийник встречен 2 раза
```

То есть примерно раз в 1.5 секунды.

## Дефект: пассивный пробник срабатывает через раз

При такой частоте окно `probeSerial` в 2.5 секунды обязано ловить серийник всегда.
Фактически — лотерея, 2 попытки из 4:

```
07:29:06 Probing for aircraft serial... -> No serial detected
07:30:45 Probing for aircraft serial... -> Aircraft identity: 1581F9DEC25AQ02998T5
07:30:51 Probing for aircraft serial... -> No serial detected
07:30:57 Probing for aircraft serial... -> Aircraft identity: 1581F9DEC25AQ02998T5
```

Разбор исключён как причина: регулярка `(?<![0-9A-Z])1581[0-9A-Z]{12,18}(?![0-9A-Z])`
на реальных байтах захвата находит серийник (перед ним идёт `0x21`, lookbehind не мешает),
буфер 64 КиБ не переполняется. Похоже, прокси 40007 распределяет поток между
подключёнными клиентами, поэтому одиночное окно видит лишь часть кадров.

Вывод для приложения: одной попытки мало, нужны повторы с переоткрытием сокета —
но короткие, потому что удерживать 40007 нельзя.

## После перезапуска: серийник в шине есть постоянно

Первые замеры после перезапуска показали тихую шину (1–21 кадр за окно, серийника
почти нет), но это оказался артефакт — борт в тот момент выключался. На реально
работающем борту, **без всякого захода в «Информацию»**:

```
окно 3с #1: кадров=128  серийник есть
окно 3с #2: кадров=128  серийник есть
окно 3с #3: кадров=128  серийник есть
```

То есть у Mini 5 Pro серийник в шине присутствует всё время, пока борт включён,
и заход в «Информацию» для этого не нужен. Этим он принципиально отличается от
Lito X1, где кадр приходит строго как push на открытие того экрана.

## Надёжность зависит не от длины окна, а от числа попыток

При серийнике, присутствующем в каждом трёхсекундном окне захвата, штатный пробник
приложения даёт **3 успеха из 6**. Замер захватов с разной длиной окна (по 6 попыток):

```
окно 1000 мс: пойман 3/6
окно 1500 мс: пойман 6/6
окно 2500 мс: пойман 3/6
```

Удлинение окна не помогает — 2500 мс работает не лучше 1000 мс. Похоже, прокси 40007
распределяет поток между подключёнными клиентами, и исход решается в момент
подключения, а не длительностью прослушивания.

Отсюда практический вывод: пробнику нужны **повторные короткие попытки с
переоткрытием сокета**, а не одно длинное окно. Три попытки по 1.5 с занимают порт
не дольше нынешней одной на 2.5 с, но доводят вероятность до практически единицы.

## Дефект: смена борта оставляет чужой серийник

При подключённом Mini 5 Pro статус показывал:

```
aircraft_model_code  WA150
aircraft_model_name  DJI Mini 5 Pro
aircraft_serial      1581FB34C25CF0032AAG   <- серийник Lito X1
```

Модель обновилась с экрана DJI Fly, а серийник остался от предыдущего борта.
Эта химера ушла в статистику и осела в истории `controller_aircrafts` как

```
1581FB34C25CF0032AAG  DJI Mini 5 Pro
```

то есть серийник Lito X1 подписан чужой моделью. Исправляется на клиенте сбросом
`aircraft_serial` при подтверждённой смене борта; серверный фикс защищает только
`installations`, историю он восстановить не может — запись нужно чистить вручную.
