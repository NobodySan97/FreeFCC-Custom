## Ошибка resolver

Использованный `scan_registrations.py` хранит последние 24 инструкции и
распознаёт только такую запись непосредственного значения:

```python
m = re.match(r"^(w\d+), #(0x[0-9a-f]+|\d+)$", ops)
if mn in ("mov", "movz") and m:
    regs[m.group(1)] = int(m.group(2), 0)
```

Форма `mov w0, wzr`, которая задаёт `cmd_set=0x00`, под это выражение не
попадает. Старое значение `w0` при этом остаётся в `regs`, потому что разбор
идёт по линейному окну без учёта базовых блоков и без остановки на предыдущем
вызове. В результате:

```text
0x1d051f0  mov w0, #0x3
0x1d05200  bl  0x282689c       -> 03:CD

0x1d05208  mov w0, wzr
0x1d0520c  mov w1, #0x7
0x1d05218  bl  0x282689c       -> фактически 00:07
```

Но generated output ошибочно содержит:

```text
cmd_set 0x03 cmd_id 0x07   sites: 0x1d05218
```

Та же ошибка видна для последовательных registrations `00:08`, `00:09`,
`00:0A` и `00:0C`. Она также объясняет ложные пары, где старое значение пришло
из другого ближайшего registration, например `0x15d7818` было записано как
`10:01`, хотя перед вызовом установлен `w0=wzr`.

Это не только пропущенная строка таблицы: ошибка одновременно создаёт ложные
пары и скрывает настоящие. Поэтому нельзя исправить результат простым
добавлением строки `cmd_set=0x00`.

### Итог по `06:72` / `06:74`

Пара закрыта по имени и wire-format:

- `06:72` — `set stick value lock`;
- `06:74` — `get stick value lock`;
- оба legacy-кадра FreeFCC устанавливают `ch0..ch4=0`, `ch5=1`;
- последний байт — `ch5f`, сначала `0x00`, затем `0xff`.

Это действительно команда семейства блокировки значений органов управления,
а не region/FCC write. При этом точный физический эффект `ch5=1` и различие
`ch5f=00/ff` всё ещё требуют live-проверки. Поэтому формулировка «найдена
команда блокировки стика» корректна на уровне firmware name, а утверждение
«какой именно стик и как именно блокируется этими значениями» пока открыто.

После сопоставления с RC Pro 2 порядок каналов заявлен как
`A/E/T/R/WH1/WH2`. Legacy payload меняет именно `ch5`, то есть по этой модели
`WH2`. Пользователь отдельно указал на существовавшие жалобы о блокировке
колёсика при работе старой схемы. Это независимое field corroboration:
последовательность

```text
firmware name `stick value lock`
→ payload `ch5=1`
→ предполагаемое соответствие `ch5=WH2`
→ наблюдаемый дефект колёсика
```

сильно поддерживает причинную связь старого keepalive с блокировкой колёсика.
Точная роль дополнительного `ch5f=0x00/0xff` из этого не следует.

### Неполное описание `extra`

Raw-данные содержат:

```text
0x08005444: 06 a4 00 00 00 00 00 00 41 ad 01 08
```

То есть у `06:A4` primary target нулевой, но третье `u32` равно
`0x0801ad41`. Текущий документ говорит о втором указателе только у `06:77` и
`00:0B`, поэтому описание поля неполно. При правильной базе `0x0801ad40`
находится внутри payload, и значение похоже на ещё один Thumb pointer.
Семантику `extra` и особый случай нулевого primary handler у `06:A4` следует
уточнить отдельно; на вывод по `06:72` это не влияет.

## Review полной карты MCU (`e02553a`)

### Точные редакционные ошибки

1. В документе написано «21 команда `cmd_set=0x06` (две с нулевым handler)».
   Фактически таблица содержит **23 записи** `cmd_set=0x06`: 21 с ненулевым
   handler и ещё два нулевых слота (`06:2F`, `06:A4`). Вместе с четырьмя
   `cmd_set=0x00` это даёт заявленные 27 записей.
2. Фраза «два handler'а не отправляют ответ» перечисляет три обработчика
   `cmd_set=0x06`: `06:77`, `06:A2`, `06:AC`.

### Ограничение структурного scanner

`mcu_sig.py` не строит CFG. Он линейно дизассемблирует с адреса handler и
останавливается на первом `pop {...,pc}` или `bx lr`. Поэтому:

- `insns` — длина первого линейного фрагмента до первого возврата, а не
  доказанная длина всего тела функции;
- наличие прямого `bl 0x08018a70` надёжно показывает использование известного
  response helper в просмотренном фрагменте;
- отсутствие такого `bl` **не доказывает отсутствие ACK**: ответ может лежать
  в другой ветке CFG, tail-call или вызываемой подпрограмме.

Следовательно, таблицу можно использовать как первичную структурную
инвентаризацию, но вывод «`06:77`, `06:A2`, `06:AC` и все `00:xx` не отвечают»
нужно ослабить до «в линейно просмотренном фрагменте нет прямого вызова
идентифицированного response helper» либо подтвердить полным CFG/manual
disassembly.

### Граница соответствия каналов

В RC520 подтверждены две разные функции:

- handler `get stick value lock` по `0x08032330`, который читает шесть байт
  stick-lock state и возвращает 7 байт;
- код по `0x0803d08a`, который логирует packed RC state как
  `A/E/T/R/WH1/WH2`.

Само наличие этих строк в одном firmware и общий RC-control context делают
соответствие `ch0…ch5 = A/E/T/R/WH1/WH2` сильным `DERIVED`-выводом. Для
строгого `CONFIRMED` нужен data-flow от одного и того же channel buffer либо
явное индексное сопоставление. Полевой симптом блокировки колёсика является
важным независимым подтверждением именно для `ch5/WH2`, но не объясняет
семантику `ch5f`.

### Поправка cross-generation ID

Последующий анализ RC520 обнаружил его таблицу диспетчера в другом формате:

```c
struct rc520_entry {
    uint32_t handler;
    uint8_t  cmd_id;
    uint8_t  cmd_set;
    // flags...
};
```

Raw-записи и прямые строки handlers дают:

| Платформа | Set | Get |
|---|---|---|
| RC2 / `rc331` | `06:72` | `06:74` |
| RC Pro 2 / `rc520` | `06:74` | `06:84` |

В RC520 raw table рядом лежат:

```text
handler 0x08032db1, id=74, set=06  → "set stick lock ..."
handler 0x08032331, id=84, set=06  → "get stick value lock ..."
```

Поэтому утверждения `e02553a`, что RC520 содержит «ту же пару команд» и что
`06:74` cross-confirmed как get на двух поколениях, неверны. RC520 независимо
подтверждает формат stick-lock state и 7-байтовый readback, но **ID были
перенумерованы между поколениями**.

Это локальный drift, а не полная несовместимость таблиц. Из 21 активного
`cmd_set=0x06` ID RC2 **20 присутствуют и в RC Pro 2**; единственное
исключение — `06:A2`. То есть пользователь прав: большинство индексов, фактически
почти весь активный набор RC2, сохраняются. При этом совпадение номера не
гарантирует одинаковую семантику: именно `06:72` и `06:74` показывают
перестановку операций внутри в основном стабильного ID-корпуса.

Одноразовый `rc520_table.py` также нельзя использовать от указанного в
scratchpad начала без исправления: его `valid()` разрешает только ограниченный
набор command set и отвергает первую реальную запись `cmd_set=0x03`, возвращая
`0 records`. Сама 37-entry выемка была получена позднейшим ad-hoc parser без
этого фильтра и требует сохранения воспроизводимого исправленного scanner.

### Review вывода `a0296d1` по `10:58`

Generic scanner из коммита не доказывает заявленный отрицательный результат:

1. Он вычисляет `has_adr`, но не использует его в условии, поэтому наличие
   callback в `x2` фактически не проверяется.
2. Он считает любой `bl`, если в линейном окне остались какие-либо константы
   `w0/w1`; нет ограничения на target registrar.
3. Output содержит невозможные однобайтовые `cmd_id`: `0x100`, `0x1A58`,
   `0xFFFF` и другие. Это прямое наблюдение сильного загрязнения.
4. Как и первый WA530 scanner, он не понимает `wzr`, не строит CFG и может как
   создавать false positives, так и пропускать настоящие registrations.

Фраза документа «helper по строке не локализуется» также неверна. Функция
`0x1f30bc0`:

- получает исходные `w0=cmd_set`, `w1=cmd_id`, `x2=callback`, `x3=context`;
- без изменения аргументов вызывает нижний registrar `0x1f33ae0`;
- в error path использует literal `vp_message_set_req_callback`.

Это и есть точный wrapper, по которому возможен строгий scan.

Независимый проход нашёл **113** прямых `bl 0x1f30bc0`:

- 106 call sites разрешаются непосредственными значениями `w0/w1`;
- `10:58` среди них отсутствует;
- семь sites формируют хотя бы один аргумент не непосредственной константой.

Дополнительный ручной разбор семи sites дал:

| Call site | Результат |
|---:|---|
| `0x1165e84` | `00:DE`: `w0=0` следует из предшествующего `cbz`, `w1=DE` |
| `0x14127bc` | 4 пары из статической таблицы: `22:90`, `22:83`, `22:96`, `22:99` |
| `0x1412b2c` | 11 пар: `0A:55`, `06:50`, `03:5D`, `03:6B`, `03:65`, `03:4B`, `22:A3`, `22:A6`, `22:A2`, `04:70`, `22:A4` |
| `0x1c0e960` | 14 пар `cmd_set=0x11`: ID `3A`, `38`, `0A`, `0B`, `03`, `0F`, `30`, `31`, `32`, `33`, `34`, `0C`, `40`, `06` |
| `0x14e8678` | `cmd_id=2A` фиксирован, `cmd_set` динамический; это не `10:58` |
| `0xe160d8` | оба значения runtime (`w21/w20`) |
| `0x117fde8` | значения читаются из caller-supplied table |

Таким образом, `10:58` отсутствует во всех непосредственно и статическими
таблицами восстановленных registrations WA234. Остались **два динамических
механизма**, которые текущим статическим срезом не закрыты. Корректная
формулировка: «не найден среди статически восстановленных registrations; два
runtime-fed механизма остаются», а не «не регистрируется в WA234».

## WM260 ARM32: начальная проверка scanner

| Поле | Значение |
|---|---|
| Файл | соседний corpus `wm260/extracted/dji_perception` |
| Размер/формат | ELF32 ARM, Android 23, stripped |
| SHA-256 | `76a08fcf22db6c9a66c9a01192bbc0984d078a5329d8d8d7f946c45fe0e90822` |
| Build ID | `136fcec833fc5af8eac717e1785c38e4` |
| Registration error string | `Failed to set req callback for command [0x%x, 0x%x] since callback table is uninitialized` |

Первый `scan_reg_arm32.py` пока не соответствует заявленной стратегии:

- `find_string()` существует, но вообще не вызывается;
- target helper не локализуется и не используется как фильтр;
- весь `.text` независимо дизассемблируется сначала как Thumb, затем как ARM,
  хотя это создаёт ложные инструкции на участках другого mode;
- сохраняется линейное окно значений через calls/branches;
- считаются любые `bl/blx` с похожими `r0/r1`.

Его output может служить только поисковой эвристикой. Для вывода по `10:58`
нужны xref error string → конкретный set-request-callback registrar, корректная
карта ARM/Thumb функций и scan только вызовов этого registrar.

### Фактический output и преждевременный вывод

Завершившийся Thumb-проход выдал:

```text
13947 candidate call(s), 880 distinct pairs
hottest targets:
  0x6e0c98 x1754
  0xbe2c24 x1375
  0x88ee4 x1299
10:58 -> 0
```

Это не отрицательное доказательство. Число кандидатов на два порядка больше
реалистичного количества регистраций, а вызовы распределены по множеству
неидентифицированных targets. Команда была передана через `head`, поэтому в
сохранённом результате нет даже второго ARM-прохода. Следовательно, фраза
«WM260 тоже даёт `10:58 -> 0` — четвёртая платформа» имеет статус
`UNVERIFIED` и не должна попадать в основной справочник.

Тем не менее, commit `35b7268` записал этот результат в
`WA234_READBACK_ANALYSIS.md` как «отсутствует» и в commit subject сформулировал
`rule out 10:58 on WM260`. Это проверяемо неверный уровень уверенности:
отсутствие пары среди загрязнённых heuristic candidates не исключает её среди
настоящих регистраций.

## `dji_wlm` v576: за ID-таблицу ошибочно принята `.rela.dyn`

В свежем проходе Claude принял данные с file offset `0x6880` за начало
24-байтового массива handlers и подписал 79 «первых полей» через mini-symbol
ELF. Проверка ELF sections опровергает эту интерпретацию:

```text
.rela.dyn  file offset 0x3930, size 0x5370, entry size 0x18
           диапазон 0x3930..0x8c9f
```

Таким образом, `0x6880` находится **внутри `.rela.dyn`**, а размер «записи»
24 байта просто совпал с размером `Elf64_Rela`. Более того, выбранное начало
сдвинуто на одно 64-битное поле. Каждая напечатанная тройка имеет вид:

```text
addend предыдущей relocation |
r_offset следующей relocation |
r_info следующей relocation (= 0x403, R_AARCH64_RELATIVE)
```

Например, строка scanner:

```text
08: wlm_process_forward_pkt | 0x206eb0 | 0x403
```

получена из двух соседних relocation. `0x0cac3c` — addend записи с
`r_offset=0x206e98`, тогда как `0x206eb0/0x403` уже относятся к следующей
relocation с addend `0x1583fc`. Это не одна command descriptor.

Даже до проверки section boundary полученная нумерация противоречила уже
восстановленной таблице `51:*`:

| Handler | Ранее подтверждённый ID | «Слот» нового массива |
|---|---:|---:|
| `wlm_process_forward_pkt` | `51:01` | `08` |
| `wlm_link_mode_query` | `51:0A` | `13` |
| `wlm_modem_onoff_control` | `51:19` | `19` |
| `wlm_service_mode_switch_req` | `51:1A` | `1A` |
| `wlm_bind_status_changed` | `51:22` | `22` |

Первые два несовпадения уже исключали правило «номер записи = command ID».
Поздние совпадения (`19`, `1A`, `22`) оказались случайными.

Итог:

- весь `wlm51_table.txt` как таблица ID **INVALID**;
- он не является даже самостоятельным массивом handlers;
- имена функций в addends реальны, но `.rela.dyn` содержит relocations всего
  бинарника и не доказывает, что конкретная функция зарегистрирована в
  command set `0x51`;
- для восстановления ID по-прежнему нужен код регистрации/dispatch или
  настоящая command table, а не relocation stream.

Commit `35b7268` добавил этот ложный «слот-лист» в
`RC_PRO2_DUML_COMMAND_REFERENCE.md`; весь добавленный раздел от заголовка
«Полный слот-лист таблицы `dji_wlm` v576» до следующего раздела требует
удаления либо полной замены после нахождения реальной структуры.

### Исправленные уровни уверенности

- «`10:58` не зарегистрирована» заменено на «не найдена среди статически
  разрешённых регистраций»: WA530 resolver неполон, WA234 оставляет два
  runtime-fed пути, WM260 heuristic scanner непригоден для negative-вывода.
- Отсутствие `51:19/1A/22` на RM510 ограничено восстановленной статической
  таблицей; иной runtime route не исключён.
- Отсутствие handler pointers/relocations в aircraft `dji_sys`, `dji_wlm`,
  `dji_sdrs_agent`, `dji_network` доказывает только, что этот конкретный
  relocation-приём не восстанавливает таблицу.
- Карта RC2 MCU исправлена до 23 записей `cmd_set=0x06` (21 активная + два
  нулевых primary slots), а отсутствие прямого response helper больше не
  приравнивается к отсутствию ACK.

## Итог review для FreeFCC

Непосредственно опасные или доказанно посторонние части текущей программы:

1. Оба `06:72` в FCC core на RC2 записывают stick-lock state и могут затрагивать
   `WH2`/колесо; на RC Pro 2 тот же ID вызывает другую неизвестную функцию.
2. `03:F9 max_height=500` изменяет полётный лимит и не относится к FCC.
3. `ce_restore.json` отправляет тот же stick-lock payload на другого,
   неподтверждённого получателя и не имеет доказанной CE-семантики.

Их следует удалить из приложения. Остальные opaque кадры нельзя объявить
необходимыми, но исторический составной профиль был аппаратно проверен как
целое. Без нового A/B-теста безопасная граница изменения — убрать только
подтверждённо посторонние/рискованные операции и сохранить остальной core.
