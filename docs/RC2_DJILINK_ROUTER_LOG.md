# Router-лог DUML на RC 2: адресация узлов и что из него видно

Дата: 2026-08-08. Стенд: пульт **DJI RC 2** (`6UZBL7H02101J6`, прошивка
`V14.00.00.04 test-keys`), борт **Avata 360** (`wa530`, `03:E0` →
`crc=430bd5b7 count=1561`), серийник борта `1581FA8JC264600B31QZ`.

Всё ниже — разбор логов самого пульта. Ни одной записи параметров не
выполнялось; DUML-запросы, упомянутые как наши, были read-only
(`03:E0`, `03:E1`, `03:F8`, `00:51`).

Сырые логи не коммитятся (1.1 МБ, `local/rc2-logs/`, в `.gitignore`).

## Зачем это

Порты `40007/40008/40009` отдают приложению только входящий поток: все кадры
идут `dst=0x02`, а **запросов DJI Fly к борту в них нет**. `tcpdump` на
loopback недоступен — это требует `CAP_NET_RAW`, то есть root, которого на
пульте нет (`su` в termux — заглушка, а заводское dev-приложение даёт
`uid=1000(system)`, но не `uid=0`).

Router-лог — обходной путь: демон `dji_link` сам печатает в `logcat`
маршрутную информацию каждого проблемного сообщения шины, включая
исходящие от приложения.

## Как включается

В заводском приложении `com.dpad.fuli` (开发助手), кнопка `Log`
(`LogcatLog`). Из декомпиляции — три независимых механизма:

| Что | Как |
|---|---|
| Общий включатель | `setprop prop.sys.debuglog 1` |
| Конкретный линк | Binder-сервис `djilink`, транзакция **1053**, аргументы `(linkId, on)` |
| Маска тегов | `persist.dji.debug` — список через запятую (`protocol`, `services`, `systemui`, `update`, `launcher`) |

| 6 | сокет `127.0.0.1:40007` |

его можно забрать без system-шелла.

## Граница метода

**В лог попадают только аномалии.** Все 2295 разобранных строк — уровня `E`
или `F`; записей уровня `I`/`D` с полем `message=` нет вовсе. Контексты:
`EVENT_SEND`, `MB_FORWARD`, `EVENT_HANDLE`, `EVENT_RECV`.

Отсюда два следствия, которые легко нарушить при интерпретации:

- **Счётчики сообщений не отражают долю в трафике.** «`03:E0` ×770» означает
  «770 раз не доставлено», а не «770 раз послано». Успешная доставка не
  логируется, поэтому доли успеха по этому логу вычислить нельзя.
- **Payload в логе отсутствует.** Есть `cmd_set`, `cmd_id`, `seq_id`, `attr`,
  адреса отправителя и получателя — и всё. Сырых кадров (`55 ..`) в логах
  нет; поиск hex-последовательностей не дал ни одного совпадения. Значения
  параметров и селекторы полей по-прежнему добываются только реальным
  запросом.

## Адресация узлов

Строка лога выглядит так:

```text
[LINK_DEBUG-EVENT_SEND-TARGET] Can't find the target ctx when auto update
sequence id: -1007. Detail: seq_id=65535 message=0x000300e0
with attr=0x00000140 from machine=0x0000 host=0x0205
to machine=0x0000 host=0x1704
```

- `message=0x00SS00II` → `cmd_set = байт[1]`, `cmd_id = байт[3]`. Здесь
  `0x000300e0` = `03:E0`, `0x00000051` = `00:51`, `0x00510019` = `51:19`.
- `machine` во всех 2295 строках равен `0x0000`.
- `host=0xTTII` → **`TT` = тип устройства, `II` = индекс**, и это ровно та
  пара, из которой собирается байт адреса DUML:

```text
dst = (type & 0x1f) | (index << 5)
```

Раскладка проверена по четырём независимо известным значениям — совпадение
точное, поэтому статус `CONFIRMED`:

| host | type / index | dst | Чем подтверждается |
|---|---|---|---|
| `0x0300` | 3 / 0 | `0x03` | `flight:0`, адресат наших `03:xx` |
| `0x0200` | 2 / 0 | `0x02` | `sender=2` в `led_on.json` |
| `0x0204` | 2 / 4 | `0x82` | `sender=130` в `fcc.json` |
| `0x0d00` | 13 / 0 | `0x0d` | RC; та же константа у стороннего клиента |
| `0x0907` | 9 / 7 | `0xe9` | `vt_air:7` = `dji_wlm`, см. `RM510_DUML_COMMAND_REFERENCE.md` |
| `0x0e07` | 14 / 7 | `0xee` | шлюз `0xEE` из `AVATA360_4G_RESEARCH.md` |

Полный список узлов, встреченных в этой сессии:

| host | dst | Кто это |
|---|---|---|
| `0x0200` | `0x02` | приложение, слот 0 |
| `0x0204` | `0x82` | приложение, слот 4 |
| `0x0205` | `0xa2` | приложение, слот 5 — под ним работает DJI Fly |
| `0x0300` | `0x03` | полётный контроллер |
| `0x0801` | `0x28` | тип 8, индекс 1 |
| `0x0804` | `0x88` | тип 8, индекс 4 — источник идентификации |
| `0x0907` | `0xe9` | `vt_air:7` = `dji_wlm` |
| `0x0a01` | `0x2a` | тип 10, индекс 1 |
| `0x0a05` | `0xaa` | тип 10, индекс 5 |
| `0x0d00` | `0x0d` | пульт |
| `0x0e00` | `0x0e` | тип 14, индекс 0 |
| `0x0e04` | `0x8e` | тип 14, индекс 4 |
| `0x0e06` | `0xce` | тип 14, индекс 6 |
| `0x0e07` | `0xee` | шлюз идентификации |
| `0x1704` | `0x97` | тип 23, индекс 4 — назначение неизвестно |

Тип 14 (`0x0e`) владеет адресом `0xEE`, у которого в
`FIRMWARE_CORPUS.md` до сих пор значилось «владелец route `0xEE`» как
открытый вопрос. Лог отвечает на половину: `0xEE` — это узел **типа 14 с
индексом 7**. Само имя семейства из лога не следует; кандидат — LTE-ветка,
потому что в `dmesg` присутствует демон `dji_lte`, но это догадка, а не
факт.

## Что летало по шине

| `set:id` | Записей | Маршрут | Что это |
|---|---:|---|---|
| `03:E0` | 770 | `0x0205 → 0x1704` (390), `0x0e04 → 0x1704` (380) | запрос паспорта таблицы параметров |
| `00:81` | 483 | `0x0d00 → 0x0a01` (319), `→ 0x0204` (151), `0x0200 → 0x0d00` (8) | heartbeat линка |
| `00:82` | 428 | `0x0d00 → 0x0a01` (271), `→ 0x0204` (157) | heartbeat линка |
| `51:19` | 310 | `0x0e04 → 0x0907` | к `dji_wlm`; набор `0x51` — управление устройствами |
| `03:43` | 279 | `0x0300 → 0x0a05` | от полётного контроллера |
| `00:51` | 16 | `0x0804 → 0x0205` | идентификация, см. ниже |
| `ee:0c` | 5 | `0x0e07 → 0x0200` | от шлюза `0xEE` |
| `09:a0` | 3 | `0x0e00 → 0x0e06` | ветка SDR |
| `00:88` | 1 | `0x0801 → 0x0205` | версия |

Поле `attr` устойчиво связано с командой: `0x00000140` у всех `03:E0`,
`0x00001040` у heartbeat и `ee:0c`, `0x00000040` у `00:51` и `00:88`,
`0x00000080` у `09:a0`, `0x00000000` у `51:19` и `03:43`. Похоже на битовую
маску флагов доставки; расшифровка не проверялась.

## Отдельные наблюдения

**`00:51` — периодическая раздача идентификации.** Все 16 записей идут
`0x0804 → 0x0205`, то есть от узла `dst=0x88` к слоту DJI Fly, и это не
ошибки, а `EVENT_HANDLE-MONITOR: Handle timeout up to 11…16 ms` —
предупреждение о медленной обработке. Интервалы: `8.2 s` и кратные ему
(`16.5`, `57.7`), то есть период раздачи ≈ 8.2 s, а пропуски объясняются
тем, что в лог попадают только медленные случаи. Этот же узел `0x88` в
пассивном захвате шины отдавал кадры `00:E5` и `00:32`, несущие серийник
борта и серийник пульта. Запрос серийника разобран отдельно: `00:51` с
однобайтовым селектором поля в payload, см. `duml-serial-query`.

**`03:E0` в никуда.** Все 770 записей — `Can't find the target ctx when auto
update sequence id: -1007` с `seq_id=65535` (`0xFFFF`, то есть номер не
присвоен), адресат `0x1704`. Отправители — и DJI Fly (`0x0205`), и модуль
`0x0e04`. При этом наш собственный `03:E0`, посланный напрямую на
`dst=0x03`, стабильно отвечает. Вывод: маршрут к таблице параметров через
`0x1704` на этой конфигурации не разрешается, а прямое обращение к
полётному контроллеру работает. Что такое `0x1704` и почему на него
рассчитывает штатное приложение — открытый вопрос.

**Порт 40007 — это видеозеркало.** В логах `dji_link trans_utils`
(`stream_conf_run`) видны `multi_hdr = 0x55aa55aa`, `xdhdr = 0x6d`, `ch = 1`,
`len = 4128`. Сигнатура `0x55aa55aa` — не DUML (`0x55`), а поток FPV.
Это объясняет давнее наблюдение, что удержание `40007` рвёт связь DJI Fly с
бортом: канал общий с видео.

**Демоны пульта** (по `dmesg`): `dji_link`, `dji_lte`, `dji_blackbox`,
`dji_wlm`, `dji_sdrs_agent`, `dji_primary_battery`, `dji_rc_upgrade`,
`dji_logs`, `dji_amt`.

**Идентификаторы в логах `wl_mgr`.** Борт `1581FA8JC264600B31QZ` фигурирует с
`hash="0x3ca6ad40"`, встречается и `hash="0x3e3f6fbe"`. Это device-hash
менеджера радиолинка, **не** хеш параметра из `FLYC_PARAM_TABLE.md` — путать
их нельзя.

## Классификация ошибок роутера

| Контекст | Текст | Записей |
|---|---|---:|
| `EVENT_SEND-TARGET` | `Can't find the target ctx … -1007` | 770 |
| `EVENT_SEND-WAIT_LIST` | `Timeout to wait ack` | 610 |
| `MB_FORWARD-TARGET-TABLE` | `Can't find target rt table when forward on host 0205` | 279 |
| `MB_FORWARD-TARGET-TABLE` | `Can't find target rt table when send on host 0e04` | 154 |
| `MB_FORWARD-N/A` | `Router error -1002 on host 0205` | 298 |
| `EVENT_SEND-ASYNC_SEND` | `Send event in async mode error: -1007` | 156 |
| `EVENT_HANDLE-MONITOR` | `Handle timeout up to N us` | 16 |
| `EVENT_RECV-EVENT_DISPATCH` | `Can't find ack wait event registered` | 8 |
| `EVENT_HANDLE-N/A` | `Handle event error: -1001` | 4 |

Коды: `-1007` — нет контекста/цели, `-1002` — ошибка роутера, `-1001` —
ошибка обработки. Ошибки сосредоточены на узлах, которых в этой конфигурации
нет (`0x1704`, `0x0a01`, `0x0a05`, `0x0907`), поэтому сами по себе они не
означают неисправности линка.

## Что метод не дал

- Захват payload — нужен `tcpdump`, то есть root.
- Полную картину трафика — только аномалии.
- Запрос серийника от самой DJI Fly: на инфо-экране она шлёт лишь `03:E0`, а
  идентичность держит в кэше. Чтобы увидеть её обращение за серийником, нужно
  заставить перечитать идентичность — переподключить борт при активном логе.

## Воспроизведение

```bash
# на пульте, из system-шелла
logcat -G 16M && logcat -b main -c        # расширить и очистить буфер
# спровоцировать событие в DJI Fly
logcat -d -b main > /sdcard/dpad-test/capture.txt

# на ПК
grep -a 'LINK_DEBUG' capture.txt |
  grep -oE 'message=0x[0-9a-f]{8}.*host=0x[0-9a-f]{4} to machine=0x[0-9a-f]+ host=0x[0-9a-f]{4}'
```

Скрипт разбора — `local/rc2-logs/analyze.py` (не коммитится).
