# RM700 (DJI RC Pro) — MCU DUML-таблица

Разбор прошивки `V02.02.0803_rm700_dji_system.bin` (DJI RC Pro, умный пульт для
Mavic 3). Источник — сетевая шара `dji_firmware`, загружена пользователем
2026-07-25. Контейнер — обычный tar (`rm700.cfg.sig` первым элементом), три
модуля.

| Модуль | Версия | `enc_key` | Что внутри |
|---|---|---|---|
| `0205` | v01.26.00.13 (2023-12-26), 1.40 ГБ | UFIE/… | Android A/B OTA (не распакован в этом заходе) |
| `0600` | v20.06.00.06 (2023-10-24), 181 КБ | **пусто** | MCU-прошивка GD32, plaintext — разобрана ниже |
| `1301` | v00.06.10.20 (2023-11-06), 72 МБ | **пусто** | gzip→tar «pigeon» с под-образами под TBIE |

MCU-модуль `0600`: `auth_key=PRAK`, `enc_key` пустой → образ открытый.
`BUILD Oct 24 2023 21:15:44`, ядро GD32 (`gd32_drv_*`, `DJI V1 Protocol`,
`DJI HOST Protocol`). Размер 180 712 байт, SP `0x20016d38`, reset vector
`0x08010631`.

Загрузочная база — **`0x08010000`**, как у RM510 (не `0x08000000`, как было
записано в первой редакции этого файла). Доказательства:

1. При базе `0x08010000` reset указывает на file+`0x630`, и там канонический
   `Reset_Handler`: `ldr r0,[pc]; blx r0; ldr r0,[pc]; bx r0`, а следующие
   векторы (`0x08010638`, `0x0801063a`, …) — заглушки `b .`. При базе
   `0x08000000` по тому же VA лежит середина чужой функции.
2. Литеральные пулы. Ни на одну строку образа нет ссылки при базе
   `0x08000000`; при `0x08010000` у каждой ровно одна:
   `set stick value lock` ← `0x0801fa8c`, `get stick value lock` ←
   `0x0801f20c`, `BUILD …` ← `0x0801c3e4`.
3. Плотность внутренних указателей: 1025 слов образа попадают в диапазон при
   базе `0x08010000` против 458 при `0x08000000`.

## Таблица команд

Формат записи — тот же «обратный», что у RC Pro 2 (`rc520`) и RM510: 12 байт
`{u32 handler(thumb) | u8 cmd_id | u8 cmd_set | u16 fa | u16 fb | u8 x | u8 y}`.
У всех рабочих записей `fa=0x0100 fb=0xffff x=00 y=ff`; финальная запись —
терминатор с `fa=0x0006 fb=0xff00`.

## Сопоставление с ранее разобранными пультами

Новых команд у rm700 **нет ни одной**. Первая редакция этого файла объявляла
новыми `06:2D/2E/58/6C/6D/7C/85` и кросс-сетовые `03:43`, `0D:27`, `01:80`,
`19:43` — все они уже присутствуют в таблицах RC Pro 2 (`rc520`) и/или RM510,
см. [`RC_MCU_DUML_COMMAND_MAP.md`](RC_MCU_DUML_COMMAND_MAP.md).

Реальная картина:

- Набор `0x06` у rm700 **совпадает с RM510 в точности** — те же 29 ID, без
  расхождений в обе стороны.
- Вся таблица rm700 — **строгое подмножество rc520**: 34 записи против 37,
  разница ровно в трёх — у rc520 дополнительно `06:55`, `06:F7` и `00:98`.

| Пульт | Записей | `0x06` | Прочие наборы |
|---|---:|---:|---|
| RC2 (`rc331`) | 27 | 23 | `00:01/07/0B/0C` |
| RM510 | 36 | 29 | `00:01/07/0B/0C/FF` |
| **RC Pro (`rm700`)** | **34** | **29** | `00:00`, `01:80`, `03:43`, `0D:27`, `19:43` |
| RC Pro 2 (`rc520`) | 37 | 31 | `00:00/98`, `01:80`, `03:43`, `0D:27`, `19:43` |

Единственное, что действительно делит линейку по этому признаку —
**кросс-сетовые маршруты** (кадры чужих наборов, на которые MCU пульта отвечает
сам): они есть у rm700 и rc520 и отсутствуют у RC2 и RM510.

| Кадр | Набор | Имя в публичном диссекторе |
|---|---|---|
| `03:43` | FLYC | `OSD General Data Get` |
| `0D:27` | BATTERY | без имени |
| `01:80` | SPECIAL | без имени |
| `19:43` | набор `0x19` | набор публично не документирован |

## `06:72` / `06:74` / `06:84` — где rm700 в споре «поколений»

rm700 несёт **все три** ID одновременно. Здесь разбор **string-proof**: обе
строки грузятся инструкцией внутри тела самого обработчика, а не берутся из
соседнего литерального пула.

- **`06:74`** `0x0801fa40` — **сеттер**. `ldr r5,[r0,#0x1c]` — указатель на
  payload; `ldr r1,[r5]` → `str r1,[r0]` и `ldrh r1,[r5,#4]` → `strh r1,[r0,#4]`
  переносят **6 байт из кадра** в структуру состояния (её отдаёт `0x8024e2c`).
  Затем `ldr r1,[pc,#0x1c]` = `0x0803b348` = `WARNING:set stick value lock:
  ch0%d … ch5%d`, вызов лога через указатель из `0x08035ea0`, ответ **1 байт**.
- **`06:84`** `0x0801f1c0` — **геттер**. Payload не читает; берёт структуру у
  `0x8024e2c` и копирует из неё 6 байт в буфер ответа `sp+0x11`, логирует
  `0x0803b304` = `WARNING:get stick value lock: ch0%d … ch5%d`, ответ **7 байт**
  (`movs r2,#7` — статус + шесть каналов).
- **`06:72`** `0x0801f888` — **не stick lock**: `movs r2,#1; movs r0,#2;
  ldr r1,[r4,#0x1c]; bl 0x802d248`, ответ 1 байт. Это байт в байт та же
  «запись байта в персистентный параметр №2», что у RC Pro 2 (`0x8040f08`) и
  RM510 (`0x8027f84`). Строк нет, смысл параметра — `UNKNOWN`.

То есть по оси set/get **rm700 ложится на схему RC Pro 2 / RM510**
(`74`=set, `84`=get), а не на схему RC2 (`72`=set, `74`=get). Тезис
«исключение — это RC2» не ослаблен, а подтверждён на четвёртом пульте, причём
впервые сразу строками. См. [[RC_MCU_DUML_COMMAND_MAP]].

> Первая редакция этого файла утверждала обратное (`06:72` — сеттер шести
> каналов, rm700 в группе RC2). Тот разбор велся по базе `0x08000000`, то есть
> по байтам, смещённым на 64 КБ относительно настоящих обработчиков, и целиком
> недействителен.

Строка декодирования каналов присутствует и здесь:
`WARNING:A:%d E:%d T:%d R:%d WH1:%d WH2:%d c1:%d c2:%d fo:%d pho:%d rec:%d
f_m:%d c3:%d rc_m:%d pau:%d wheelmode %d` — подтверждает **четыре оси + два
колеса** (`WH1`, `WH2`) и камерные кнопки (focus/photo/rec) из собственной
прошивки rm700. Загружается она из общего телеметрийного хелпера
(единственная ссылка — `0x080294a4`), а не из handler'а. Мелкое отличие от
RC2/rc520/RM510: там те же строки идут с префиксом `INFO:`, здесь — `WARNING:`.

## Метод и воспроизведение

1. `tar xf V02.02.0803_rm700_dji_system.bin` → три `.pro.fw.sig`.
2. `dji_imah_fwsig.py -u -f -i rm700_0600_*.pro.fw.sig -m rm700_0600` (PRAK,
   `enc_key` пустой) → `rm700_0600_0600.bin`.
3. База `0x08010000` — проверяется тремя тестами выше; таблица найдена
   сканером записей rc520-формата, полный экстент — прогулкой по stride-12,
   пока `handler` попадает в диапазон образа.
4. Обработчики `72/74/84` — capstone Thumb, база `0x08010000`, литералы
   резолвятся как `((pc+4) & ~3) + disp`.

Проверка базы обязательна до любого дизассемблирования: у DJI-шных GD32
модулей `0600` образ начинается с векторной таблицы, но грузится не с
`0x08000000`, а после бутлоадера. Быстрый тест — посчитать, при какой базе
строки образа вообще имеют литеральные ссылки.

Ключи-инструменты в scratchpad: `mcu_scan_rc520fmt.py` (беззатравочный поиск
таблицы), `disasm_thumb.py` (`MCU_BASE=0x08010000`).
