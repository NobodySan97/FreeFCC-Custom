# RC MCU (`rc331`, `rc520`): полная карта DUML-команд

Дата анализа: 2026-07-24.

Продолжение [`RC331_MCU_FIRMWARE.md`](RC331_MCU_FIRMWARE.md), где найден первый
незашифрованный образ MCU пульта и расшифрована `06:72`. Здесь разобраны **все**
команды, зарегистрированные в этом MCU, и добавлено кросс-подтверждение с
RC Pro 2.

Границы результата задаются честно: имена в этой прошивке есть только у двух
команд, поэтому остальные описаны структурной сигнатурой (что читают, чем
отвечают, какие подпрограммы вызывают), а не догадками о назначении.

Ни одна команда на реальное устройство не отправлялась.

## Корпус

| Образ | Размер | SHA-256 | База | Строк |
|---|---:|---|---|---:|
| `rc331_0600` (RC2) | 108 136 | `f5ee13337efe61a8e60801a0e21275745a9bcb44277ef45617421471f836beea` | `0x08005000` | 298 |
| `rc520_0600` (RC Pro 2) | 211 920 | распакован из `V01.00.0700_rc520` | `0x08020000` | 774 |

Оба модуля имеют `type=MCU` и **пустой `enc_key`**. `rc520_0600` идентичен во
всех четырёх локальных OTA RC Pro 2 (`V01.00.0400`…`V01.00.0700`): версия
модуля везде `v10.02.01.21_20250825`.

## Что такое шесть каналов

Расшифровка присутствует **в обеих прошивках**, а не только в RC Pro 2 — в
`rc331_0600` строка лежит по file offset `0x11617`:

```text
 A:%d E:%d T:%d R:%d WH1:%d WH2:%d                                  (RC2)
WARNING:A:%d E:%d T:%d R:%d WH1:%d WH2:%d c1:%d c2:%d fo:%d …       (RC Pro 2)
```

То есть `ch0…ch5` = **A** (aileron), **E** (elevator), **T** (throttle),
**R** (rudder), **WH1**, **WH2** — четыре оси двух стиков плюс два колеса.

### Независимая проверка: у RC2 действительно два колеса

Прошивка RC2 содержит ровно **шесть** телеметрических ключей аналоговых
органов управления, и они закрывают все шесть каналов:

| Ключ в `rc331_0600` | Орган |
|---|---|
| `fw_0600_l_s_x`, `fw_0600_l_s_y` | левый стик, две оси |
| `fw_0600_r_s_x`, `fw_0600_r_s_y` | правый стик, две оси |
| `fw_0600_l_wheel` | левое колесо |
| `fw_0600_right_wheel` | правое колесо |

Отдельные имена для левого и правого колеса снимают сомнение: MCU RC2
обслуживает два колеса, а не одно. Рядом в той же группе лежат счётчики
кнопок (`Key_cnt_c1`, `Key_cnt_c2`, `Key_cnt_shutter`, `Key_cnt_focus`) и
калибровочные поля (`cal_min`, `cal_mid`, `cal_max`), то есть это штатная
таблица параметров органов управления, а не отладочный остаток.

Остальные поля строки — кнопки и режимы (`c1`, `c2`, `c3`, фото, запись,
flight mode, RC mode, пауза, режим колеса). Рядом лежат
`drv_rc_stick_init`, `dji_joystick_init`, `rcstick_push_init`.

Это закрывает вопрос, к чему относятся `ch0…ch5` в `06:72`/`06:74`:
к органам управления пульта, а не к радиотракту.

## Кросс-подтверждение на RC Pro 2

В `rc520_0600` та же пара команд присутствует со своими строками
(`get stick value lock: ch0%d … ch5%d`). Handler по `0x08032330`:

```asm
push {r4,r5,r6,lr}
bl   0x8038bd4        ; -> r0 = указатель на состояние stick-lock
ldr  r1, [r0]         ; 4 байта  -> буфер
ldrh r1, [r0, #4]     ; +2 байта -> буфер
ldrb r1,[r0,#2] … ldrb r2,[r0]   ; шесть байт в лог
blx  <printf>
ldrb r0, [r5, #7]
cbz  r0, out
movs r2, #7           ; длина ответа = 7 байт
add  r1, sp, #0x10
bl   0x803c630        ; отправка ответа
```

Ответ ровно **7 байт** — шесть каналов плюс седьмой байт. Это независимо
подтверждает формат payload, восстановленный на RC2.

## RC Pro 2: таблица найдена, нумерация другая

Второй проход по `rc520_0600` нашёл его диспетчерскую таблицу — она устроена
иначе, чем на RC2: тот же размер записи 12 байт, но **другой порядок полей**.

```c
struct rc520_cmd_entry {   // 12 bytes
    uint32_t handler;      // thumb-указатель, идёт ПЕРВЫМ
    uint8_t  cmd_id;
    uint8_t  cmd_set;
    uint16_t flags_a;      // всегда 0x0100 у команд протокола
    uint16_t flags_b;      // всегда 0xffff
    uint8_t  x, y;         // 0x00, 0xff
};
```

Основная таблица — по `0x0804fb0c`, 37 записей:

| Command set | Команды |
|---|---|
| `0x06` | `01`, `03`, `04`, `19`, `1A`, `2D`, `2E`, `31`, `32`, `38`, `55`, `56`, `58`, `6B`, `6C`, `6D`, `72`, `74`, `77`, `7B`, `7C`, `7D`, `7E`, `84`, `85`, `A5`, `A6`, `AC`, `AD`, `F5`, `F7` |
| `0x00` | `00`, `98` |
| `0x01` | `80` |
| `0x03` | `43` |
| `0x0D` | `27` |
| `0x19` | `43` |

Итого 31 команда `cmd_set=0x06` против 23 записей на RC2 (21 активный handler
и два слота с нулевым primary handler) — набор шире, но не является
надмножеством: у RC2 есть `06:A2`, которой в этой таблице нет.

Кроме основной, в образе есть ещё восемь коротких таблиц того же формата
(`0x0802002c`, `0x08020180`, `0x080233a4`, `0x08037a44`, `0x0804cfa8`,
`0x0804e78c`, `0x0804e7cc`, `0x0804e830`) — они содержат наборы вроде
`00:07/0B/0C/FF`, `10:80/82`, `45:B3/B7/CB/D7`, `49:AB/BB/CD`. Их роль не
установлена; часть значений выглядит как совпадение по формату, а не как
настоящая таблица команд, поэтому в карту они не включены.

### Имена, восстановленные на RC Pro 2

Строки грузятся внутри самих handler'ов, поэтому атрибуция надёжна:

| Команда | Handler | Строка в прошивке |
|---|---|---|
| `06:01` | `0x080323d8` | `get utc year %d month %d day %d hour %d minute %d second %d send_id %d send_index %d` |
| `06:32` | `0x08032e78` | `set utc year %d month %d day %d hour %d minute %d second %d send_id %d send_index %d` |
| `06:74` | `0x08032db0` | `set stick lock ch0:%d ch1:%d ch2:%d ch3:%d ch4:%d ch5:%d ch5_f:%d` |
| `06:84` | `0x08032330` | `get stick value lock: ch0%d ch1%d ch2%d ch3%d ch4%d ch5%d` |
| `06:7E` | `0x0803228c` | `cali_info dead_zone ch[%d] dead_zone %d m_l %d m_h %d` (строка в вызываемой функции) |

### Что `06:72` делает на RC Pro 2

Handler `0x08032bfa` разобран полностью:

```asm
push {r3, r4, r5, lr}
movs r2, #1              ; size = 1 байт
movs r0, #2              ; index = 2
ldr  r1, [r4, #0x1c]     ; указатель на payload
bl   0x8040f08           ; param_write(index, src, size)
ands r1, r0, #0xff
bne  ack                 ; ошибка -> сразу ответ
bl   0x8041af4           ; успех -> сохранить блок в хранилище
ack:
ldrb r0, [r4, #7]
cbz  r0, out
movs r2, #1              ; длина ответа = 1 байт
bl   0x803c630           ; отправка ACK
```

Разбор вызовов:

- `0x8040f08` — обёртка `param_write(index, src, size)`. Она получает дескриптор
  поля через `0x80472b0` — это `switch` по индексу `0x00..0x0F`
  (`tbb [pc, r0]`), возвращающий пару «адрес поля, размер». Для `index = 2`
  адрес — `0x2002a718 + 2`, размер 1 байт; проверка размера в обёртке требует
  совпадения с переданным.
- `0x8041af4` вызывает `0x80359be(id = 1, buf = 0x2002a718, size = 0x3E)` —
  сохранение всего блока **62 байта** в хранилище с id 1, то есть параметры
  персистентные.

Тот же механизм используют другие команды RC Pro 2, что и подтверждает
трактовку структуры как таблицы параметров:

| Команда | index | size |
|---|---:|---:|
| `06:7D` | `00`, `05`, `06`, `07`, `08`, `09`, `0A` | 1 и 4 |
| `06:72` | `02` | 1 |
| `06:77` | `04` | 1 |
| `06:6B` | `05` | 1 |
| `06:55` | `08` | 1 |
| `06:56` | `0C`, `0D`, `0E` | 14, 14, 1 |
| `00:00` | `0F` | 1 |

Итог: на RC Pro 2 `06:72` — **запись одного байта в персистентный параметр
с индексом 2 и последующее сохранение блока параметров**, с ответом из одного
байта статуса. Это никак не связано со stick lock: тот работает со своей
структурой `0x20022ad4` (её отдаёт `0x8038bd4`) и глобалом `0x20022adc`, а не с
`0x2002a718`.

Чего установить не удалось: **какой именно параметр** лежит по индексу 2.
Прошивка не логирует ни имени поля, ни назначения; строк в handler'е нет.
Поэтому уровень — `CONFIRMED` для механизма и адреса, `UNKNOWN` для смысла
параметра.

### Третий пульт: RM510 — и он совпадает с RC Pro 2, а не с RC2

2026-07-25 в корпус добавлена прошивка `V03.02.0700_rm510_dji_system.bin`
(SHA-256 `978e3f005e1236c29067d2112fc63abbd5aa2a2446faccdf2b87889607b74bb9`).
Её модуль `0600` — снова **не зашифрован**:

```text
name=0600   type=GD32   version=10.04.01.15   date=2022-10-12   enc_key=
```

Распакованный образ — 159 972 байта, SHA-256
`10cae99bcba5a2e61f12eb785c60444e728fcf1ef84cb335e50e7650221b5053`,
`ARM Cortex-M`, SP `0x20016550`, reset `0x08010618`, база `0x08010000`.
Тип модуля здесь указан как `GD32` (у RC2 и RC Pro 2 — `MCU`).

Таблица команд лежит в том же формате, что у RC Pro 2
(`{u32 handler, u8 cmd_id, u8 cmd_set, u16 flags}`), 36 записей:

| Command set | Команды |
|---|---|
| `0x06` | `01`, `03`, `04`, `19`, `1A`, `2D`, `2E`, `31`, `32`, `38`, `56`, `58`, `6B`, `6C`, `6D`, `72`, `74`, `77`, `7B`, `7C`, `7D`, `7E`, `84`, `85`, `A5`, `A6`, `AC`, `AD`, `F5` |
| `0x00` | `01`, `07`, `0B`, `0C`, `FF` |

Строки в handler'ах:

| Команда | Строка |
|---|---|
| `06:74` | `INFO:set stick value lock: ch0%d … ch5%d` |
| `06:84` | `INFO:get stick value lock: ch0%d … ch5%d` |
| `06:32` | `INFO:set utc year %d month %d …` |
| `06:01` | `INFO:get utc year %d month %d …` |
| `06:72` | строк нет |

### Вывод: исключение — это RC2, а не «старое поколение»

Раскладка `74` = set / `84` = get совпадает у **RM510 и RC Pro 2**. Уникален
именно RC2 (`rc331`), где `72` = set, `74` = get.

Хронология это подтверждает: RM510 — `v10.04.01.15` от 2022-10-12, RC Pro 2 —
`v10.02.01.21` от 2025-08-25, RC2 — `v10.06.00.50` от 2025-11-03. То есть RC2
не «старше» и не «новее» по схеме — он просто другой.

Более того, `06:72` в RM510 — **байт в байт та же функция**, что на RC Pro 2:

```asm
movs r2, #1          ; size = 1
movs r0, #2          ; index = 2
ldr  r1, [r4, #0x1c] ; payload
bl   0x8027f84       ; param_write   (аналог 0x8040f08 в rc520)
bne  ack
bl   0x80287a0       ; persist       (аналог 0x8041af4)
ack:
movs r2, #1
bl   0x8024830       ; ACK длиной 1 байт
```

Значит `06:72` = «записать байт в персистентный параметр №2» — это норма для
линейки, а stick lock на этом ID есть только у RC2.

Строка расшифровки каналов (`INFO:A:%d E:%d T:%d R:%d WH1:%d WH2:%d …`)
присутствует и здесь, то есть набор из четырёх осей и двух колёс общий для всех
трёх пультов.

### Нумерация зависит от поколения — важно для FreeFCC

| Операция | RC2 (`rc331`) | RC Pro 2 (`rc520`) |
|---|---|---|
| set stick lock | **`06:72`** | **`06:74`** |
| get stick value lock | **`06:74`** | **`06:84`** |
| `06:72` | set stick value lock | другой handler (`0x08032bfa`) |

То есть один и тот же кадр `06:72` на двух пультах попадает в разные
обработчики. На RC Pro 2 `06:72` — короткая функция: вызывает подпрограмму
`0x8040f08` с константой `2`, при нулевом результате — `0x8041af4`, и отвечает
**одним байтом** статуса. Строк у неё нет, назначение остаётся `UNKNOWN`.

Практический вывод: исторический профиль FreeFCC, отправляя `06:72`, на RC2
писал stick lock, а на RC Pro 2 дёргал совсем другую функцию. Поэтому оба
кадра удалены из текущего FCC core и из runtime assets.

Отдельно: попытка привязать строки к handler'ам по близости literal pool
(«ближайший предшествующий handler») даёт ложные срабатывания — соседние
функции делят пулы, и, например, `19:43` получал строку `get stick value lock`.
Этот метод отброшен; в таблицах выше только строки, загружаемые инструкцией
внутри самой функции или её прямого вызова.

| Смысл `ch0…ch5` | `CONFIRMED` как набор: строка `A:%d E:%d T:%d R:%d WH1:%d WH2:%d` присутствует в обеих прошивках, а шесть ключей `fw_0600_l_s_x/y`, `r_s_x/y`, `l_wheel`, `right_wheel` подтверждают два стика и два колеса у RC2. `DERIVED` остаётся только привязка порядка `ch0…ch5` к этому набору: внутри stick-lock handler нумерация не печатается |
| Имена команд | На RC2 — только `06:72`/`06:74`; на RC Pro 2 добавились `06:01`, `06:32`, `06:74`, `06:84`, `06:7E`. Остальные обе прошивки не логируют: обход вызовов на глубину 4 не нашёл ни одной строки |
| Внешние имена | 9 из 21 активной команды `0x06` совпадают с выемкой из `dji_test_userlibs.dll`; это имена уровня DJI Test Platform, а не самой прошивки |
| Таблица команд в `rc520_0600` | `CONFIRMED`: `0x0804fb0c`, 37 записей, порядок полей обратный (handler первым); 31 команда `cmd_set=0x06` |
| Эффект `06:72` на поведение пульта | `UNKNOWN`: требует live-теста с наблюдением `06:74` readback |

В линейно просмотренных фрагментах `06:77`, `06:A2`, `06:AC` и четырёх
`00:xx` нет прямого вызова известного response helper. Это не доказывает
отсутствие ACK: ответ может находиться в другой CFG-ветке, tail-call или
вызываемой подпрограмме. Поэтому отсутствие live ACK для этих команд нельзя
интерпретировать только по этой структурной таблице.

## Инструменты

Одноразовые скрипты (в `scratchpad`, вне репозитория):

| Скрипт | Назначение |
|---|---|
| `mcu_table.py` | поиск таблицы команд и подбор базы загрузки по границам функций |
| `mcu_handler_strings.py` | строки, на которые ссылается сам handler |
| `mcu_deep.py` | рекурсивный обход вызовов (глубина настраивается) с поиском строк |
| `mcu_globals.py` | атрибуция «немых» handler'ов через общие RAM-глобалы |
| `mcu_sig.py` | структурные сигнатуры: helper'ы, уникальные подпрограммы, сравнения |
| `disasm_thumb.py` | дизассемблирование диапазона (база через `MCU_BASE`) |

Все используют capstone; распаковка модулей — `dji_imah_fwsig.py -f -u` из
`dji-firmware-tools` с `pycryptodome` в отдельном venv.
