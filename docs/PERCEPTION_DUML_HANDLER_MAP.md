# WA530 `dji_perception`: карта зарегистрированных DUML-обработчиков

Дата анализа: 2026-07-24.

Этот документ отвечает на один вопрос, который в
[`DUML_COMMAND_AUDIT.md`](DUML_COMMAND_AUDIT.md) до сих пор стоял как открытый:
какие `cmd_set:cmd_id` действительно принимает получатель `bvision:0`, и есть
ли среди них `10:58` из FreeFCC-профилей.

Главный результат: механизм регистрации локализован, но исходный линейный
сканер восстановил список неполно и часть вызовов классифицировал неверно.
Среди корректно разрешённых статических регистраций **`10:58` не найдена**,
однако это не доказывает её полного отсутствия: остаются вызовы с
runtime-аргументами и неразрешённые способы загрузки констант. Историческая
подпись «AUTOTEST enter service mode» этим корпусом не подтверждается.
Command set `0x10` у perception действительно принадлежит
autotest/fstest-подсистеме, но в доказанном наборе занимает другие ID.

## Как восстановлен список

1. В `.rodata` найдены строки регистрации:
   `cmd_set:0x%x cmd_id:0x%x register FAIL.`,
   `cmd_set: %d, cmd_id: %d, callback has been register!`,
   `[AUTOTEST] cmd_set:%u cmd_id:%u have set v1_req_callback`.
2. Потоковый разбор `.text` (capstone, aarch64) нашёл ADRP+ADD-ссылки на эти
   строки. Одна из них, `0x6fa290`, используется в развёрнутой цепочке
   регистраций по адресам `0x1542c00`–`0x15430c8`.
3. Общий helper этих цепочек — `0x282689c`. Его собственные log-строки
   (`0x6410b5`, `0x896ad1`) идентифицируют его как
   **`vp_message_set_req_callback`**, тонкую обёртку над `0x2829c70`.
4. По всему `.text` собраны вызовы `bl 0x282689c` и восстановлены аргументы:
   `w0 = cmd_set`, `w1 = cmd_id`, `x2 = callback`. Где `cmd_id` грузится как
   `ldrb w1, [xN]` после ADRP+ADD, байт прочитан прямо из образа.

Исходный скрипт сообщил **139 из 151** call site и 133 уникальные пары, но эти
числа нельзя считать покрытием. Он не распознавал, например, `mov w0, wzr`
(`cmd_set=0`) и переносил устаревшие значения регистров через границы
линейного окна. Не менее 15 прямых регистраций `cmd_set=0` были из-за этого
классифицированы неверно. Таблица ниже сохраняется как полезный
восстановленный срез, но не как полный реестр.

## Что это даёт по `10:58`

| Утверждение | Статус |
|---|---|
| `10:58` регистрируется в WA530 `dji_perception` | **Не подтверждено**: отсутствует среди корректно разрешённых статических регистраций; полный отрицательный вывод невозможен |
| Command set `0x10` принадлежит autotest/fstest | `CONFIRMED`: цепочка `0x1542c00`–`0x15430c8`, общий callback `0x1543274` содержит `req_autotest_handle_cb`, `fstest_adapter_handle_cmd`, `fstest_adapter_push_obse` |
| Набор autotest-ID | `CONFIRMED`: байтовая таблица по VA `0x47044ec` даёт `01 02 03 04 05 06 07 08 09 10 11 12 13 14 15`; отдельно зарегистрированы `1B`, `22`, `23`, `81`, `90` |
| «AUTOTEST enter service mode» как подпись `10:58` | **Не подтверждается** этим корпусом: строка `[AUTOTEST] ==> Request(seq:%u) to enter autotest(host:%04x->%04x)` существует, но доказанной связи именно с `0x58` нет |

Ограничение: вывод относится к WA530 V01.00.0300. Он не переносится
автоматически на другие платформы и не доказывает, что кадр не обрабатывается
вообще: runtime-аргументы, нераспознанные способы формирования аргументов и
возможные обработчики в других процессах остаются вне этого среза.

Проверка на WA234 (полный дамп eMMC) также не нашла `10:58` среди разрешённых
статических регистраций, но оставила два runtime-fed механизма — см.
[`WA234_READBACK_ANALYSIS.md`](WA234_READBACK_ANALYSIS.md).

WM260 `dji_perception` (SHA-256 в [`FIRMWARE_CORPUS.md`](FIRMWARE_CORPUS.md))
не содержит ни одной строки `AUTOTEST` — подсистема появилась в
WA530-поколении. Его регистрация использует другой текст
(`Failed to set req callback for command [0x%x, 0x%x] since callback table is
uninitialized`) и 32-битный ARM; отдельный скан для него не выполнялся.

## Побочный результат: имена обработчиков `0x0a`

Callback-функции, зарегистрированные рядом, называют себя сами:

| Команда | Callback | Имя внутри функции | Что делает | Уровень |
|---|---|---|---|---|
| `0a:56` | `0x25f1ab0` | `vp_general_ctrl_switch` | `Perception switch command is received from 0x%02x%02x, switch_type: %u, msg_length: %u`; ветки `led#%u light_mode = %d power %d`, `unimplemented_switch_command`, `Sub-command type is invalid` | `CONFIRMED` |
| `0a:58` | `0x25f209c` | `vp_general_get_switch` | `Perception get switch command is received from 0x%02x%02x, cmd_mode=%u`; читает `flashlight led_ctr_status=%d active_status=%u power=%u`, `temp`, `power` | `CONFIRMED` |

Это отдельная пара control/readback внутри Vision command set. Совпадение
`cmd_id = 0x58` с FreeFCC-кадром `10:58` — только совпадение ID при разных
command set; никакого доказательства, что исторический кадр «на самом деле»
адресовался сюда, нет. FreeFCC LED-профили используют не этот путь, а
`03:F9` PM-write, поэтому связь остаётся неподтверждённой гипотезой.

## Воспроизведение

Скрипты разбора одноразовые и лежат вне репозитория (`scratchpad`):
`scan_autotest.py` (поиск ссылок на строки), `scan_registrations.py`
(первичный, неполный разбор `cmd_set`/`cmd_id` у вызовов helper),
`disasm_range.py`, `read_va.py`, `strings_in_range.py`. Все они читают ELF
через `readelf -SW` и capstone; `pyelftools` в системе отсутствует. Числа
покрытия из первичного `scan_registrations.py` нельзя использовать как
доказательство отсутствия команды без проверки каждого call site.
