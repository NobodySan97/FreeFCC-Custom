# End-to-end путь 4G (Enhanced Transmission): результат двух трейсов

Дата: 2026-08-11. Метод: свежее дизассемблирование Ghidra 12.1.2 headless
(проекты/скрипты/декомпиляции — `.scratch/reverify_20260811/`), hash/Build ID
артефактов сверены до анализа. Источники:
`lte_4g_path_trace.md` (dji_lte RC Pro 2 v576 + WA530) и
`wlm_link_switch_trace.md` (dji_wlm RC Pro 2 v576).

Документ отвечает на главный открытый вопрос проекта: **какая цепочка реально
включает 4G, и что из неё доступно внешнему клиенту**.

## Полная цепочка (обе платформы)

```
[1] SDR pairing (dron↔пульт по SDR)
        │  после SDR pairing со стороны SDR приходит кадр cmdset 0x09 id 0x85
        ▼
[2] dji_lte: get_peer_sdr_info_0985 (v576 0xd4658 inline; WA530 0x141170)
        │  validate sender/SSFN → vtable reinit → set_bind_info → do_pair
        ▼
[3] pairing FSM: NoBindInfo→UnPair→Pairing→Paired
        │  программирует liblte auth/crypt/session
        ▼
[4] lte_paired_global_nego_cb → 51:41 ability push в dji_wlm
        │  (51:42 = result req/ack; lte_query_wlm_nego_result)
        ▼
[5] dji_wlm узнаёт о LTE: beacons (wlm_beacon_msg_handler →
        wlm_set_local_comp_lk_sta_for_link_type) + пуши 51:03/13/1B/41/42
        │  comp_lk_sta[LTE] := 1. АВТОПЕРЕКЛЮЧЕНИЯ НЕТ (CONFIRMED xref+decompile)
        ▼
[6] Приложение (DJI Fly / FreeFCC) шлёт 51:1A (или 51:02) в dji_wlm
        │  gate: HYBRID_LTE_SDR на liveview отвергается resp(3,3,3),
        │  пока comp_lk_sta[LTE]==0; SN должен найтись в peer dev list
        ▼
[7] dji_wlm FSM link_sw (9 состояний, таблица 0x20c868):
        Idle→Trigger→Negotiation(fmsg с peer wlm)→Agent Prepare(51:07)
        →Route Switch(51:05)→Completion→Wait Peer Result(51:06)→fin
        │  таймаут 3000 ms, 3 watchdog; сбой → Exception/Undo со старым режимом
        ▼
[8] Агенты (dji_lte/sdrs_agent/wifi) выполняют физическое переключение;
        dji_lte: 51:07 → lte_link_ctrl_proc_uav/gnd (v576 0xd0ec8/0xd2390;
        WA530 0x13c180/0x13dd70) — проверка eligibility (conn_state, peer LTE
        version, dongle expiry, subscribe state) и 1-байтный ACK (0=allow/1=reject)
```

## Кто что делает — разделение ролей

- **dji_lte**: activation dongle (`00:32`), SIM/eSIM, dial (только внутренний
  модем-task, из DUML недостижим), pairing FSM, ability negotiation,
  eligibility-ACK на 51:07. НЕ отправляет 51:1A/51:02 (movk-scan по v576:
  исходящие только 51:01/03/13/1B/41/42).
- **dji_wlm**: единственный владелец link-switch (FSM link_sw). Физически ничего
  не переключает — командует агентами через 51:07/51:05.
- **Приложение**: инициатор финального переключения. После `51:41/42` ничего
  само не происходит — решение принимает app («send link switch result to app»).

## Входные точки по платформам

| Действие | RC Pro 2 (v576) | WA530 |
|---|---|---|
| Запуск pairing клиентом | **Невозможен** — ждёт UAV-driven `09:85` | `18:52` (cmd 2, method=1) → `18:54` (cmd 1) → `18:53` (bind entries); gated `support_pair_byserver` |
| Teardown LTE link | 51:07 → `lte_link_ctrl_proc_gnd` | `18:56` (только tag=1 → `lte_link_disconnect_all_trigger`); это teardown, не mode switch |
| Финальный switch | `51:1A` / `51:02` в dji_wlm | то же |
| eSIM config | `18:4B` (ops 1–6), не запускает ничего напрямую | то же |
| `18:31 sdr_pair_done_handler` | stub | stub |

**DJI cloud для обычного 4G не нужен**: путь 09:85 serverless (CONFIRMED).
By-server pairing (18:53/54) — WA530-only альтернатива с bind-записями от
app/cloud; открытый вопрос — может ли не-облачный клиент сконструировать
приемлемые bind entries.

## Ключевые payloads

- `51:1A` `wlm_service_mode_switch_req`: `{ver, service_type (0=LIVEVIEW,
  1=DOWNLOAD), mode (liveview: 0=SDR, 1=HYBIRD, 2=WIFI; download: 0=COMMON,
  1=WIFI_HIGHSPEED), SN-строка}`. Невалидные type/mode → resp(9,9,9).
- `51:02` `wlm_link_mode_sw_trigger`: 3 байта link-mode `{cmd, liveview,
  common_data}`, `0xFF` = hold.
- `18:52` `lte_pair_method_req`: `[ver(=0), cmd_type, data_len, new_method@4]`;
  cmd 2 = set (method 0=off/1=on), cmd 3 = query.
- `18:56` `lte_link_ctrl_req`: `[tag@0, data_len@1]`; только tag=1.

## Практическое следствие для FreeFCC

1. Минимальная клиентская последовательность на RC Pro 2: дождаться
   pairing+negotiation (`comp_lk_sta[LTE]==1`), затем **один** кадр `51:1A`
   `{00, 00, 01, SN}` — именно это реализовано в коммите `73b5665` (замена
   128-кадрового sweep). Старый sweep с prefix `00 00 00` просил mode=SDR —
   гарантированный no-op; upstream v1.5.4 независимо пришёл к тому же байту.
2. Условие успеха — уже спаренный/активированный dongle (стадии 1–5). Клиент
   на v576 pairing инициировать не может; если LTE не виден, запрос будет
   отвергнут resp(3,3,3) — стоит читать ответ и показывать причину (TODO:
   readback в send4gActivationFrames).
3. SN в `51:1A` проверяется через `wlm_peer_dev_list_find` — нужен полный
   заводской серийник `1581…`; короткий model-code почти наверняка не пройдёт
   (открытый вопрос ужесточения guard в FreeFCC).
